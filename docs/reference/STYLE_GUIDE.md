# 문서 작성 가이드

이 가이드는 Spring·Flutter·React Admin 템플릿 문서를 작성하고 고칠 때 따르는 공통 기준이에요. 문서의 역할은 현재 구현을 정확히 설명하고, 독자가 필요한 작업을 끝낼 수 있게 돕는 것이에요. 문서마다 같은 목차나 분량을 맞출 필요는 없어요.

## 1. 독자와 목적

문서를 쓰기 전에 누가 어떤 문제를 해결하려고 읽는지 정해요. 입문 안내에는 필요한 사전 지식과 첫 실행 결과를, 참조 문서에는 찾기 쉬운 규칙과 조건을 담아요.

| 독자 | 필요한 설명 | 예시 |
|---|---|---|
| Level 0: 기술을 처음 접하는 사람 | 용어의 뜻, 작업 목적, 실행 전 준비 | 프로젝트 소개, 첫 실행 |
| Level 1: 기본 사용법을 아는 개발자 | 실행 순서, 명령을 실행할 위치, 성공·실패 확인 방법 | 앱 생성, 개발 환경 설정 |
| Level 2: 구현을 수정하는 개발자 | 책임과 호출 관계, 계약, 예외, 관련 코드 | 모듈 구조, 코딩 규약 |
| Level 3: 설계를 검토하는 개발자 | 선택의 근거, 실제로 검토한 대안, 제약과 변경 조건 | ADR |

문서 처음에 목적과 전제 지식을 짧게 밝혀요. 기존 Level 분류는 읽기 순서를 안내하는 데 사용해요. 모든 문서에 같은 메타블록이나 예상 시간을 붙이지는 않아요. 시간·성능·효과를 숫자로 쓰려면 측정 조건이나 근거가 있어야 해요.

## 2. 목적에 맞는 구성

| 문서 종류 | 빠지면 안 되는 내용 |
|---|---|
| ADR | 해결할 문제, 결정과 근거, 제약·대가, 당시 상태와 관련 구현 |
| 참조 문서 | 항목의 의미, 허용 값과 기본값, 적용 조건과 예외 |
| 사용 안내 | 사전 조건, 실행 순서, 예상 결과, 실패 시 확인 방법 |
| 구조 설명 | 구성 요소의 책임, 데이터·호출 흐름, 경계와 제한 |
| 운영 절차 | 적용 상황, 진단·대응·복구 확인, 영향 범위와 주의 사항 |

이 내용이 잘 전달되면 짧은 문서는 문단 몇 개로도 충분해요. 긴 설명은 독자가 찾는 질문에 맞춰 절을 나눠요. 하나의 문서가 설명과 참조 역할을 함께 맡아도 돼요.

ADR은 당시 결정의 기록이에요. 기존 번호와 상태를 유지하고, 구현이 달라졌다면 현재 구현을 구분해 적어요. 과거 선택을 지금의 결정처럼 다시 쓰지 않아요. 결정·배경·영향을 설명하는 데 도움이 되는 대안만 비교하고, 실제 기록이 없는 경험담이나 실패 사례를 만들지 않아요. 여덟 개 절, 교훈의 개수, 외부 링크의 개수를 채우는 규칙은 적용하지 않아요.

## 3. 담백한 해요체

기본은 해요체예요. 주어와 동작을 분명하게 쓰고, 조건이 길면 조건과 결과를 나눠 설명해요. 규칙도 자연스러운 해요체로 적되 직접 인용, 코드, 오류 메시지는 원문을 유지해요. 표의 짧은 항목과 제목에는 명사형을 써도 돼요.

| 다듬기 전 | 다듬은 문장 |
|---|---|
| 같은 스크립트가 target 인자로 dev와 prod를 함께 다뤄요. | 같은 스크립트에서 인자로 dev 또는 prod를 선택해요. |
| Code References로 위임해요. | 구현 위치는 아래 코드 링크에서 확인할 수 있어요. |
| 이 문서의 위상은 모든 문서가 참조하는 메타 문서예요. | 새 문서를 쓰거나 기존 문서를 고칠 때 이 기준을 따라요. |
| 코드와 문서 사이의 정합성을 확보해요. | 문서가 실제 코드와 맞는지 확인해요. |

번역된 영어 어순을 그대로 옮기지 않아요. 불필요한 수동태와 명사 나열을 풀고, 괄호나 대시로 길게 덧붙인 설명은 별도 문장으로 옮겨요. 지나친 의인화, 감탄, 과장된 비유, 질문을 던진 뒤 바로 답하는 구성을 반복하지 않아요.

‘항상’, ‘자동으로’, ‘완전히’, ‘이것만 바꾸면’처럼 범위를 단정하는 표현에는 구현 근거가 필요해요. 수동 작업이나 예외가 있으면 같은 위치에 적어요. 문장을 짧게 만들려고 중요한 조건을 빼지는 않아요.

## 4. 용어와 표기

일반 설명에는 익숙한 한국어를 써요. `fallback`은 문맥에 맞게 ‘대체 처리’나 ‘기본값 사용’으로 설명할 수 있지만, 코드 식별자·API 이름·표준 기술 용어는 임의로 번역하지 않아요.

같은 개념은 같은 이름으로 부르고, 처음 나오는 어려운 용어는 짧게 설명하거나 용어집에 연결해요. 용어 정의를 여러 문서에서 따로 관리하지 않아요. Spring 용어는 [용어집](./glossary.md), Flutter 용어는 [Flutter 용어집](https://github.com/storkspear/docs-template-flutter/blob/main/docs/reference/glossary.md)을 기준으로 해요.

템플릿으로 만든 저장소는 ‘파생 레포’라고 불러요. GitHub의 fork 기능과 구분해요. 파일명·클래스명·환경변수는 백틱으로 표시하고 조사와 붙여 써요. 예를 들어 `AuthPort`는 인터페이스예요. 일반 링크 문구까지 모두 코드처럼 꾸밀 필요는 없어요.

## 5. 코드와 명령 예제

예제를 고치기 전에 해당 구현과 호출부를 읽어요. 함수명뿐 아니라 인자·반환값·기본값·오류·권한을 확인하고, 다른 환경이나 Mock에서만 성립하는 동작을 구분해요.

코드 블록에는 언어를 지정해요. 실제 파일을 인용하면 경로와 발췌 여부를 적고, 설명용 예제는 실제 구현과 구분해요. 생략 부호가 있는 예제를 그대로 실행할 수 있다고 안내하지 않아요. 들여쓰기는 해당 언어와 저장소의 규칙을 따라요.

명령은 실행 위치, 필요한 환경, 성공을 확인하는 방법과 함께 적어요. 파일 삭제·배포·마이그레이션처럼 상태를 바꾸는 명령은 대상과 영향 범위를 먼저 설명해요. 공개 문서에는 토큰·실제 비밀번호·개인 설정을 넣지 않고 자리표시자를 사용해요.

테스트를 통과했다는 사실과 실제 외부 서비스에서 확인했다는 사실을 구분해요. 코드만 읽은 결과를 실행 검증처럼 적지 않아요. 코드를 보고도 확정할 수 없는 외부 서비스 동작은 공식 자료나 허용된 검증으로 확인하고, 확인하지 못한 부분은 그대로 밝혀요.

## 6. 링크와 문서 통합

같은 문서 묶음의 링크는 상대 경로로 적어요. 소스 코드처럼 공개 미러에 없는 파일은 원본 저장소의 GitHub 링크를 사용하고, 비공개 저장소라면 접근 권한이 필요하다는 점을 안내해요. 외부 근거는 해당 내용을 직접 뒷받침하는 공식 문서에 연결해요.

문서의 역할과 설명하는 규칙이 같으면 정본 한 곳에 통합해요. 각 문서에만 있던 조건·예시·주의 사항을 먼저 옮긴 뒤, 목차와 내부 링크를 정본으로 바꿔요. 입문 안내와 API 참조처럼 목적이 다르면 필요한 설명을 남기고 자세한 규칙만 정본에 연결해요.

기존 파일 주소에는 짧은 이동 안내를 남겨 외부 링크가 끊기지 않게 해요. 제목을 바꾸거나 절을 합칠 때는 기존 앵커도 보존하고 알맞은 새 절에 연결해요. 앵커 규칙을 추측해서 링크를 만들지 말고 GitHub와 문서 뷰어에서 실제 이동을 확인해요.

## 7. 검토 순서와 기록

문서를 끝까지 읽고 관련 소스를 확인한 뒤 수정해요. 검색 결과 몇 줄이나 첫 문단만 보고 전체를 검토한 것으로 기록하지 않아요. 긴 문서는 구간을 나누되 읽은 범위와 남은 범위를 기록해 이어서 검토해요.

문장 교정, 사실 정정, 누락 보완, 중복 통합을 구분해 기록해요. 분량을 줄이는 것 자체를 목표로 삼지 않고, 그대로 두는 편이 낫다면 그 이유를 남겨요. 변경 뒤에는 독자의 실행 순서와 구현 사실이라는 두 관점에서 다시 읽어요.

## 8. 완료 전 확인

- 문서 전체를 읽고 주요 주장을 관련 코드·설정·테스트와 대조했는지 확인해요.
- 필수 조건, 예외, 권한, 환경별 차이, 실행 순서를 빠뜨리지 않았는지 확인해요.
- 코드 참조와 명령의 현재 형태, 문서 계약 검사 결과를 확인해요.
- 내부 링크·앵커·목차와 통합 전 주소가 올바른 곳으로 연결되는지 확인해요.
- 표·코드·그림이 PC와 모바일에서 읽히는지 확인해요.
- 원본과 공개 미러가 일치하고 내부 계획 문서가 공개 대상에 섞이지 않았는지 확인해요.

Spring 문서는 `template-spring/docs/`에서 수정해요. `tools/docs/sync-docs.sh`가 `docs-template-spring/docs/`로 복사하며, main의 자동 동기화가 같은 스크립트를 실행해요. 미러 고유 목차인 `manifest.json`은 별도로 관리해요. 파생 레포의 문서를 자동으로 덮어쓰지 않아요.

## 9. 작성 기준을 고칠 때

기준 때문에 설명이 반복되거나 사실이 왜곡되면 문서의 목적을 먼저 확인해요. 실제 수정 사례와 이유를 바탕으로 기준을 보완하고, 관련 작성 지침도 함께 맞춰요. 정해진 개수의 사례나 형식적인 예외 문구를 만들 필요는 없어요.

## 10. 변경 이력

변경 이력은 `git log -- docs/reference/STYLE_GUIDE.md`에서 확인해요. 과거 버전의 규칙과 수정 이유는 커밋 기록으로 보존해요.

## 11. 문단·표·목록·그림의 선택

이유와 결과가 이어지는 설명은 문단으로 써요. 같은 속성을 가진 항목을 비교할 때는 표를, 순서가 있는 작업은 번호 목록을 사용해요. 짧은 병렬 항목은 글머리표로 묶고, 호출 관계나 상태 전이는 필요한 경우 그림으로 보여줘요.

모든 설명에 그림·반례·요약을 넣을 필요는 없어요. 형식을 바꾸면 독자가 무엇을 더 쉽게 이해할 수 있는지 판단해요. 같은 내용을 서두·표·본문·마무리에 반복하지 않아요.

## 12. 문장을 다듬을 때

먼저 누가 무엇을 하는 문장인지 확인해요. ‘설정이 주입된다’보다 어떤 도구가 어느 파일의 값을 읽는지 적으면 독자가 수정할 위치를 알 수 있어요. 예외가 중요한 문장이라면 결과보다 조건을 먼저 설명해요.

슬래시로 나열한 일반 단어는 문장으로 풀고, 서로 다른 사실을 괄호 안에 밀어 넣지 않아요. 강조는 주의할 조건이나 핵심에만 사용해요. 줄임말을 풀어 쓰는 과정에서도 의미를 바꾸지 않도록 코드와 다시 대조해요.
